# CLI Proof-of-Work miner for JAY Network

A greenfield Node.js mining client that fetches a WebSocket token from the JAY Network API, connects to the mining pool, distributes nonce ranges across worker threads that compute SHA-256 hashes, and submits valid shares back to the pool. The architecture follows a sensible separation: config parsing, a Miner orchestrator built on EventEmitter, worker threads for CPU-bound hashing, and a display loop in the entry point.

**Watch for:** The mining loop in the worker blocks the thread's event loop, making it unable to process "stop" messages until the loop yields (confirmed). The WebSocket token endpoint is called without any authentication of the miner itself, and the token response is trusted without validation (confirmed). No tests exist anywhere in the project (confirmed).

## High-level view

The worker thread runs a tight synchronous `for` loop over up to 4 billion nonces. Because it never yields to the event loop, `parentPort.on('message')` callbacks cannot fire, meaning the "stop" message and new job messages are effectively ignored until the loop finishes or the worker is forcibly terminated. The `setImmediate(() => mine(msg))` call before starting a new job only defers one tick; once `mine()` begins, the thread is locked.

The miner connects to a hardcoded production endpoint (`mining.thejaynetwork.com`) over HTTPS/WSS, but the token fetch sends no credentials. Whatever the server returns is used directly as the WebSocket URL with no validation that it points to a legitimate endpoint. The wallet address is validated only by a prefix check (`yjay`), not by length or checksum.

The reconnection logic doubles the delay up to 30 seconds, but increments it *after* the timeout fires rather than before scheduling, so the sequence is always 1s, 2s, 4s... where the doubling lags one step behind the actual wait.

There are no tests. No unit tests for the hash computation, no integration tests for the WebSocket message handling, no tests for the config parser.

<details>
<summary>Issues (7)</summary>

1. **Worker event-loop starvation** — The synchronous mining loop blocks the worker thread's event loop, preventing it from processing stop/new-job messages. Break the loop into batched chunks using `setImmediate` to yield periodically.
2. **No token/URL validation** — The WebSocket URL returned by the token endpoint is used directly without verifying its scheme (wss://) or origin. Validate that `tokenData.wsUrl` starts with `wss://` and belongs to the expected domain.
3. **Wallet validation is cosmetic** — Only checks for a `yjay` prefix. Add length validation or a checksum check to catch typos before connecting.
4. **Reconnect delay off-by-one** — The delay is doubled *inside* the timeout callback, so the first reconnect always fires at the pre-doubled delay. Move the doubling to before `setTimeout`.
5. **No test coverage** — Zero tests for hashing correctness, nonce range splitting, config parsing, or WebSocket message handling.
6. **Worker termination race** — `stopWorkers` sends a "stop" message and immediately calls `terminate()`. The stop message will never be processed (see issue 1). The code relies entirely on `terminate()`, making the stop message dead code.
7. **Hashrate measurement resets on read** — `getHashrate()` zeroes the counter each call. If anything else calls it (or it's called at uneven intervals), the reported rate is inaccurate. Consider a sliding-window approach.

## Worker event-loop starvation

The core mining loop in `worker.js` is a synchronous `for` loop from `nonceStart` to `nonceEnd` (potentially 4 billion iterations per worker):

```javascript
for (let nonce = nonceStart; nonce < nonceEnd; nonce++) {
  if (!running || currentJobId !== jobId) {
    break;
  }
  // ... synchronous hash computation ...
}
```

The `running` flag is checked each iteration, but it can only be set to `false` by a message handler on `parentPort`. Since the event loop is blocked, that handler never fires. The thread is locked until the loop naturally ends (all nonces exhausted) or the parent calls `worker.terminate()`.

When new work arrives, `stopWorkers()` posts a "stop" message (which will never be delivered) and then immediately calls `terminate()`. The stop message is dead code. The forcible `terminate()` is the only mechanism that actually interrupts mining. Any in-progress share about to be found in the last few iterations before termination is lost.

A better pattern: break the loop into batches of ~50,000 nonces, yielding with `setImmediate` between batches. This allows the message handler to fire and set `running = false` cooperatively, enabling graceful job switching without killing threads.

## Token fetch and WebSocket trust boundary

The miner calls a POST to `https://mining.thejaynetwork.com/api/ws-token` with no body and no authentication headers. The response's `wsUrl` field is used directly as the WebSocket connection target:

```javascript
const tokenData = await this.fetchToken();
this.connect(tokenData);
// ...
const wsUrl = tokenData.wsUrl;
this.ws = new WebSocket(wsUrl);
```

No validation that `wsUrl` is a valid WebSocket URL, starts with `wss://`, or belongs to the expected domain. If the API were compromised or a DNS attack redirected the request, the miner would connect to an arbitrary endpoint and start sending wallet information and share data to it. Adding a scheme and domain check eliminates this class of redirect attack.

The `fetchToken` response also isn't checked for the expected shape. If `tokenData.wsUrl` is undefined, `new WebSocket(undefined)` throws with a cryptic error rather than a descriptive "token response missing wsUrl field" message.

## Missing tests

There are no test files, no test script in `package.json`, no test framework dependency. For a mining application where hash correctness is critical (an off-by-one in the hash input string means submitting invalid shares and wasting CPU), unit tests for the hash computation and target comparison would catch regressions. The config parser's `process.exit()` on invalid input makes it untestable without mocking; refactoring to throw would improve testability.
